Step 1

Chunking — the idea

We're building chunk_text(text, chunk_size, overlap) — a function that cuts one long string of text into smaller, overlapping pieces.

chunk_size = how many characters go in one chunk.
overlap = how many of those characters repeat at the start of the next chunk, so an idea that spans a boundary doesn't get cut in half and lose its meaning.

The number that actually matters for the loop is the step size:

step = chunk_size - overlap

This is how far the starting position moves forward for each new chunk.

text length1000
chunk_size300
overlap50
step (300 − 50)250
chunk starts0, 250, 500, 750
total chunks4

The last chunk (starting at 750) only has 250 characters left instead of a full 300 — that's expected. Whatever's left just becomes a shorter final chunk.

Step 2

The loop

Next we turn the "chunk starts" idea (0, 250, 500, 750) into an actual loop that slices the string and stops once the start position goes past the end of the text.

Walking through it by hand — len(text)=1000, chunk_size=300, overlap=50, step=250:

iter 1 · start=0text[0:300]
iter 2 · start=250text[250:550]
iter 3 · start=500text[500:800]
iter 4 · start=750text[750:1050] → really text[750:1000]
iter 5 · start=1000loop stops

Python string slicing is forgiving: text[750:1050] on a 1000-character string just returns up to character 1000, no error. That's why the shorter last chunk "just works" — no special-case code needed.

Bug caught:

the loop condition must be start < len(text), not start <= len(text). With <=, when start == len(text) (position 1000 in our example), text[1000:1300] is an empty string "" — there's no character at index 1000 in a 1000-character string (valid indices are 0–999). That extra iteration would append a useless empty chunk.

What was still missing: the sliced chunk was computed but never saved. Fix: create chunks = [] before the loop, chunks.append(chunk) inside it, and return chunks after the loop ends.

Your final, correct version:

def chunk_text(text, chunk_size, overlap):
    """Split text into overlapping chuncks of chunk_size characters."""
    step = chunk_size - overlap
    start = 0
    chunks = []
    while start < len(text):
        chunk = text[start:start+chunk_size]
        chunks.append(chunk)
        start += step
    return chunks
chunk_text complete and correct
Step 3

Running it on a real file

The concept, in plain terms: so far chunk_text only works on a string that already exists in memory. A real document lives on disk as a .txt file, so before we can chunk it we need to (1) open that file, (2) read its entire contents into one big string, (3) hand that string to chunk_text, and (4) look at what comes back to confirm it behaves the way we predicted on paper in Step 2.

Why with open(...) instead of just open(...): opening a file reserves a resource (a file handle) that the operating system needs back when you're done. with guarantees the file is closed automatically the moment the indented block ends — even if an error happens inside it. Without with you'd have to remember to call f.close() yourself, and a crash before that line would leave the file open.

Why encoding="utf-8": text files are stored as bytes on disk; an encoding is the rulebook for turning those bytes back into characters. UTF-8 is the standard that correctly handles ordinary English text as well as special characters (accents, curly quotes, etc). Leaving it out lets Python fall back to whatever the operating system's default happens to be, which can silently produce wrong characters on some systems.

Why the path is "docs/embeddings.txt" and not something longer: this is a relative path — relative to whatever folder you're standing in (your "current working directory") when you run the script. Since mini_rag.py lives in mini-rag/ and the file lives in mini-rag/docs/, running the script from inside mini-rag/ makes "docs/embeddings.txt" resolve correctly. Run the same script from a different folder and this exact path would fail.

Putting it together — read the whole file into one string, chunk it, print each result:

Step 4

Embeddings — turning chunks into vectors

The concept: sentence-transformers gives you a pretrained model. Calling model.encode(text) on any piece of text hands back a vector — a list of floating point numbers (384 numbers, for the model we're using). That vector is the model's numeric summary of what the text means.

Two chunks about similar topics get vectors pointing in a similar direction in that 384-dimensional space. Two unrelated chunks point in different directions. That single idea — comparing vector directions — is what all of search and RAG retrieval is built on top of.

First task — installation only:

pip install sentence-transformers

This pulls in torch (the deep learning library the model runs on) as a dependency, so it's a few hundred MB and can take a couple of minutes.

sentence-transformers installed

Question raised: why 384 numbers specifically, and who decides that?

384 is not a universal rule — it's a fixed property of one particular model, all-MiniLM-L6-v2, which is the model we're about to load. Whoever designed and trained that model chose an output layer with exactly 384 numbers, as a tradeoff:

Bigger vectors (768, 1024, 1536...)more nuance, more memory, slower
Smaller vectors (384 or less)faster, lighter, less precise

all-MiniLM-L6-v2 ("Mini" is in the name) was deliberately built small and fast, so 384 was the tradeoff its authors picked. A different model — OpenAI's text-embedding-3-small (1536 numbers) or Voyage's models (1024 numbers) — would give a different fixed length, because that length is baked into that model's architecture.

The rule that matters going forward: once you pick a model, every single thing you embed with it — every chunk, every question — always comes out as that same fixed length. The length is a property of the model, not something you choose per call, and (as noted back in Step 1) you must always embed with the same model for comparisons to mean anything.

Question raised: do I need to manually download all-MiniLM-L6-v2?

No — SentenceTransformer("all-MiniLM-L6-v2") downloads it automatically the first time it's called, fetching the model files from Hugging Face and caching them locally (typically under C:\Users\<you>\.cache\huggingface\). Every run after that loads instantly from the local cache instead of re-downloading. The first run being slow is expected — that's the one-time download happening.

The "meaning" isn't a hand-written rule — it emerged from training on millions of examples. Step 5

Embedding all chunks + a question, and comparing them

The problem we're solving: right now we can turn one chunk into a vector. But real retrieval needs to compare a question against every chunk, and find which chunks are most relevant. So we need:

  1. Vectors for all 14 chunks (not just chunk 0)
  2. A vector for the question itself
  3. A way to score "how similar" the question's vector is to each chunk's vector
  4. Sort by that score and pick the top few

The logic behind cosine similarity, concretely. It measures the angle between two vectors, not raw distance. The formula is:

cosine_similarity(A, B) = (A · B) / (|A| × |B|)

Where:

  • A · B is the dot product: multiply each corresponding pair of numbers and sum them up. If A = [a1, a2, a3] and B = [b1, b2, b3], then A · B = a1*b1 + a2*b2 + a3*b3.
  • |A| is the magnitude (length) of vector A: sqrt(a1² + a2² + a3²).

The result is always between -1 and 1. 1 means pointing in exactly the same direction (very similar meaning), 0 means unrelated, -1 means opposite meaning.

Practically — you don't need to hand-write this math. sentence-transformers ships a helper function, model.similarity(embeddings1, embeddings2), that computes this for you across many vectors at once. That's the practical tool; the formula above is so you understand what that function is actually computing, not magic.

Step 6

Computing similarity scores and finding the best match

The concept: we have chunk_embeddings (shape (14, 384) — 14 vectors) and question_embedding (shape (384,) — 1 vector). We want one similarity score per chunk: "how close is this chunk's vector to the question's vector?"

sentence-transformers gives you model.similarity(a, b), which compares every vector in a against every vector in b. Since our question is just one vector against 14 chunk vectors, the result is a grid of shape (1, 14) — 1 row (the one question) by 14 columns (one score per chunk).

scores = model.similarity(question_embedding, chunk_embeddings)
print(scores)
print(scores.shape)

Finding the best match. Since scores has shape (1, 14), we need the first (and only) row: scores[0]. That row has 14 numbers — one per chunk. We want the index of the largest number, not the number itself, because the index tells us which chunk to go retrieve. The tensors returned by similarity (from the torch library) have a method for exactly this: .argmax().

best_index = scores[0].argmax()
print("best chunk index:", best_index)
print("best chunk text:", chunks[best_index])

argmax = "argument that gives the maximum" — it returns the position of the highest value, not the value itself. This is a common pattern name across ML/data science, worth remembering.

Question raised: why did one tensor print with double brackets [[...]] and another with single brackets [...]?

scores — the full result of model.similarity(...) — printed as tensor([[0.2229, ...]]), shape (1, 14). Double brackets mean a 2D grid: the outer bracket is "the list of rows" (just 1 row here, since there's 1 question), the inner bracket is "the list of scores in that row" (14 of them). similarity always returns a full grid comparing every vector in the first argument against every vector in the second — even with only 1 question, it's still "1 row of comparisons."

scores[0] — indexing into that grid to grab row 0 — printed as tensor([0.2229, ...]), single brackets, 1D. Reaching in with [0] strips away one layer of structure: a single row on its own is just a plain list of 14 numbers, no longer "a grid."

Same rule as Step 5's chunk_embeddings.shape = (14, 384) vs question_embedding.shape = (384,) — the number of bracket-levels (dimensions) always matches how many levels of grouping actually exist in the data.

Step 7

Generation — turning a retrieved chunk into a real answer

The concept: chunks[best_index] is raw retrieved text, not an answer — it's just the most relevant paragraph. The final RAG step hands that paragraph to Claude along with the question, and lets Claude write an actual natural-language answer, grounded in that text.

System prompt vs user prompt, applied here (same distinction from llm_basics.txt):

  • System prompt — sets Claude's behavior for the whole exchange: "You are a helpful assistant. Only answer using the provided context. If the answer isn't in the context, say so clearly." This is what stops Claude from just using its own general knowledge instead of the retrieved chunk — grounded answers, not guesses, is the entire point of RAG.
  • User prompt — the actual content for this specific call: the retrieved chunk(s) plus the question, e.g. "Context:\n{chunk}\n\nQuestion: {question}".

The API call itself: the anthropic Python library gives you a Client object; calling .messages.create(...) on it takes a model name, a system prompt, and a messages list with the user prompt. It reads the API key automatically from the ANTHROPIC_API_KEY environment variable — no key typed into the script.

Question raised: what is "20250929" and why is it needed?

It's a release date, written as YYYYMMDD → year 2025, month 09, day 29 → September 29, 2025 — the day this specific version of Claude Sonnet 4.5 was released.

Why models are named with a date: AI labs periodically release updated versions of "the same" model — same name/tier, but retrained or improved. Without a date, the API wouldn't know which snapshot in time is meant. Pinning the exact date means:

  • The code's behavior won't silently change if a newer snapshot is released later — the exact same model version runs every time, indefinitely (while that version stays available).
  • It's reproducible — running this again in six months, or showing it to someone else, gives identical behavior, not "whatever is current now."

Same idea as pinning a package version in requirements.txt (sentence-transformers==3.0.1) instead of installing "whatever's latest" — trading a little flexibility for predictability. This particular gateway doesn't support the shorthand "claude-sonnet-4-5" as an alias for "latest," so the dated id is required here.

Cross-document retrieval — searching across all 3 docs at once

The problem: until now, the script only loaded and chunked embeddings.txt. Real retrieval needs to search across a whole knowledge base, not just one file — so the next step is loading all 3 docs (embeddings.txt, rag.txt, llm_basics.txt), chunking each one, and combining every chunk into a single list before embedding anything.

The logic: chunk each file separately (so each keeps its own text and chunk boundaries), then combine the three chunk lists with + — plain Python list concatenation, no new concept needed. Step 9

Top-3 retrieval — the answer can span more than one chunk

The problem: .argmax() only ever returns the single best-scoring chunk. Often the real answer spans a chunk boundary, or the top chunk alone is incomplete — so instead of picking 1 winner, we want the top 3 scores at once.

The concept: tensors have a method called .topk(k) — the multi-result cousin of argmax. It returns two lists at once: the top k scores themselves, sorted highest to lowest, and the chunk index each score belongs to.

top_scores, top_indices = scores[0].topk(3)

zip(top_scores, top_indices) pairs the two lists up by position so each score and its matching chunk index can be printed together in one loop — otherwise they're two separate lists that only line up by coincidence of order.

# pick the top 3 matches instead of just 1 — the answer may span chunks
# topk returns two lists: the scores themselves, and which chunk each one belongs to
top_scores, top_indices = scores[0].topk(3)
for score, idx in zip(top_scores, top_indices):
    # zip pairs each score with its matching index so they print together
    print(f"score={score:.4f} chunk={idx} text={chunks[idx][:100]}")

#2 · score 0.3786 · chunk 27"...evaluating a RAG system is its own challenge. Unlike a classification model..."
#3 · score 0.3693 · chunk 19"...states something false or made up. If the model is told to answer using only the provided context..."

Step 10

A question loop — ask repeatedly without re-running the script

The problem: every time you want to ask a different question, editing question = "..." and re-running the whole script means reloading the model and re-embedding all 44 chunks each time — even though those never change between questions.

The concept — separate what changes from what doesn't. The model and the chunk embeddings only need to be computed once. Only the question changes each round. So the loop sits after all the one-time setup (loading docs, chunking, loading the model, embedding all chunks) and wraps only the parts that depend on the question.

input(...) pauses the script and waits for you to type something and press Enter, returning what you typed as a string. break exits the loop immediately — used here so typing "quit" ends the session cleanly.

# one-time setup, outside the loop
model = SentenceTransformer("all-MiniLM-L6-v2")
client = Anthropic()  # reused every question in the loop below
chunk_combined = model.encode(chunks)

while True:
    # ask repeatedly without re-loading the model or re-embedding the docs each time
    question = input("\nAsk a question (or type 'quit' to stop): ")
    if question.lower() == "quit":
        break
    question_embedding = model.encode(question)
    scores = model.similarity(question_embedding, chunk_combined)

    top_scores, top_indices = scores[0].topk(3)
    for score, idx in zip(top_scores, top_indices):
        print(f"score={score:.4f} chunk={idx} text={chunks[idx][:100]}")

def load_and_chunk_docs(paths, chunk_size, overlap):
    """Read each doc separately, chunk it, then combine into one list
    so retrieval below searches across every doc at once."""
    all_chunks = []
    for path in paths:
        with open(path, "r", encoding="utf-8") as f:
            text = f.read()
        all_chunks += chunk_text(text, chunk_size, overlap)
    return all_chunks


def retrieve_top_k(model, question, chunks, chunk_embeddings, k):
    """Embed the question and return its top-k most similar chunks."""
    question_embedding = model.encode(question)
    scores = model.similarity(question_embedding, chunk_embeddings)
    top_scores, top_indices = scores[0].topk(k)
    return top_scores, top_indices


def generate_answer(client, question, chunks, top_indices):
    """Join the top-k chunks, ask Claude for a grounded answer."""
    context = "\n\n---\n\n".join(chunks[idx] for idx in top_indices)
    prompt = f"Context:\n{context}\n\nQuestion: {question}"
    response = client.messages.create(
        model=MODEL_NAME,
        max_tokens=300,
        system=SYSTEM_PROMPT,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.content[0].text
