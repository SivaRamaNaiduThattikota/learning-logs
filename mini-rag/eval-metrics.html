Measuring your RAG pipeline

You built retrieval and generation. Now: how do you know if either one is actually good — beyond eyeballing whether a chunk "looks relevant"? This page covers the theory, the math, and the code to measure it properly.

Concept

Why "it looks right" isn't good enough

Across the mini-rag log, every result was judged by reading the retrieved text and asking "does this look relevant?" That works for a demo with 3 documents and a handful of questions. It completely falls apart at real scale: 10,000 documents, hundreds of questions, and no time to read every retrieved chunk by eye.

Evaluation metrics replace "looks right" with a number you can compute automatically, compare across different settings (chunk size, overlap, embedding model, k value), and track over time as the system changes. Without metrics, you can't answer basic engineering questions like:

  • "Did increasing chunk overlap from 50 to 100 actually improve retrieval, or did it just feel like it should?"
  • "Is all-MiniLM-L6-v2 good enough, or would a bigger embedding model meaningfully improve results?"
  • "Is the system hallucinating more often than I think it is?"

RAG evaluation splits into two separate questions, measured separately, because a system can fail at either one independently:

Retrieval qualityDid the system find the right chunks for the question, out of everything available?
Answer faithfulnessDoes the generated answer actually match what the retrieved chunks said — or did the model drift, add things, or contradict them?
Why this split matters:

Retrieval can be perfect (the exact right chunk gets found every time) while generation still hallucinates on top of it. Or retrieval can be poor (wrong chunks) while the model still writes a fluent, confident-sounding answer — just an answer to the wrong context. A single end-to-end "did it look right" judgment can't tell you which of the two is actually broken. Measuring them separately tells you exactly where to fix something.

Setup

The answer key — ground truth for evaluation

The core idea: to measure whether retrieval got the right answer, you first need to already know what the right answer is, for a fixed set of test questions. This is called ground truth — a human-verified answer key that the automated metric checks the system's output against.

Without ground truth, there's nothing to compute a metric against — "did retrieval do well" is meaningless unless you can say "compared to what."

In code, this becomes a simple list of dictionaries — one entry per test case, pairing a question with its known-correct chunk index:

eval_set = [
    {"question": "What is cosine similarity?", "correct_index": 6},
    {"question": "What is a context window?", "correct_index": 38},

A real production eval set would have dozens to hundreds of entries, often written by domain experts who know the correct answer independently of the system being tested — the person building the eval set shouldn't be biased by watching the system's own outputs first. Five is enough to learn the mechanics.

Retrieval metrics

Measuring retrieval — Hit Rate and MRR

Two of the most common, simplest retrieval metrics — both computable from nothing more than "where did the correct chunk rank in the results?":

Hit Rate @ k

Out of all test questions, what fraction had the correct chunk somewhere in the top k retrieved results? This is a yes/no per question, then averaged.

Hit Rate @ k = (number of questions where correct chunk is in top-k) / (total questions)

If k=3 and the correct chunk appears anywhere among the 3 retrieved chunks (rank 1, 2, or 3), that question counts as a "hit." This is deliberately lenient — it doesn't care if the correct chunk was ranked first or third, only that it showed up at all within the window actually handed to the model.

Mean Reciprocal Rank (MRR)

Hit Rate treats rank-1 and rank-3 the same as long as both are "in the top-k." MRR is stricter — it rewards the correct chunk showing up higher in the ranking, not just somewhere in the window.

Reciprocal Rank = 1 / (rank of the correct chunk)
MRR = average of Reciprocal Rank across all questions

If the correct chunk is ranked #1, reciprocal rank = 1/1 = 1.0 (perfect). If it's ranked #2, reciprocal rank = 1/2 = 0.5. If it's ranked #3, reciprocal rank = 1/3 ≈ 0.33. If it's not found at all within the search window, reciprocal rank = 0. MRR is the average of these values across every test question.

Why both metrics, not just one:

Hit Rate answers "does the system usually get the right chunk into the context window at all?" — a coarse pass/fail signal. MRR answers "when it does, how confidently/highly does it rank it?" — a finer signal that Hit Rate can't see, since Hit Rate treats rank 1 and rank k identically. A system can have perfect Hit Rate but mediocre MRR if the correct chunk keeps barely squeaking into the last k-slot instead of ranking first.

In code — running the eval set through the existing retrieve_top_k function, and computing both metrics from the results:

def evaluate_retrieval(eval_set, model, chunks, chunk_embeddings, k=3):
    hits = 0
    reciprocal_ranks = []

    for case in eval_set:
        _, top_indices = retrieve_top_k(
            model, case["question"], chunks, chunk_embeddings, k
        )
        top_indices = [int(i) for i in top_indices]  # tensor -> plain ints

        if case["correct_index"] in top_indices:
            hits += 1
            rank = top_indices.index(case["correct_index"]) + 1  # 1-based rank
            reciprocal_ranks.append(1 / rank)
        else:
            reciprocal_ranks.append(0)

    hit_rate = hits / len(eval_set)
    mrr = sum(reciprocal_ranks) / len(reciprocal_ranks)
    return hit_rate, mrr

This reuses retrieve_top_k exactly as already written in mini_rag.py — evaluation doesn't need new retrieval logic, only a loop that checks the output against the answer key and tallies the results.

Generation metrics

Measuring faithfulness — did the answer stick to the context?

The problem retrieval metrics can't catch: even with perfect retrieval (correct chunk ranked #1 every time), Claude's final written answer could still drift — adding a detail that isn't in the context, or subtly contradicting it. Hit Rate and MRR only measure the search step; they say nothing about what the model did with the results.

Faithfulness (also called groundedness) asks: is every claim in the generated answer actually supported by the retrieved context? This is harder to measure than retrieval metrics, because it's a judgment about meaning, not just "did index X appear in a list."

The practical approach: LLM-as-judge

Rather than hand-writing rules to detect unsupported claims, a common and effective technique is to ask another LLM call to do the judging — give it the context, the generated answer, and ask a strict yes/no/score question about whether the answer stays within the context.

def evaluate_faithfulness(client, context, answer):
    judge_prompt = f"""Context:
{context}

Answer to check:
{answer}

Does the answer ONLY use information present in the context above,
with no added claims, facts, or details not found in the context?
Reply with exactly one word: FAITHFUL or UNFAITHFUL."""

    response = client.messages.create(
        model=MODEL_NAME,
        max_tokens=10,
        messages=[{"role": "user", "content": judge_prompt}]
    )
    return response.content[0].text.strip()

This is the same client.messages.create(...) pattern already used for generation in Step 7/11 — the only difference is the prompt's job: instead of answering a question from context, it's grading whether a different answer respects that context.

Why this works reasonably well:

Judging "does this text logically follow from this other text" is a language-understanding task, which is exactly what LLMs are good at — much harder to hand-code with rules (keyword matching, regex) than to just ask a capable model directly. It isn't perfect (the judge itself can be wrong), but it scales to hundreds of answers without a human reading every one, which manual review can't do.

What "unfaithful" actually looks like

Concretely, an unfaithful answer might: state a fact the context never mentioned (even if true in general), draw a conclusion the context doesn't support, or contradict something the context explicitly says. Faithfulness is not the same as correctness — an answer can be faithful to the context and still wrong, if the context itself was wrong or insufficient. Faithfulness only checks "did the model stay within its sources," not "are the sources right."
